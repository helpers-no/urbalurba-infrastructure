## The one decision this plan is not free to make: never the bootstrap key

Garage's own setup (`047-setup-garage.yml`) denies its bootstrap key (`GARAGE_ACCESS_KEY`/
`GARAGE_SECRET_KEY`) create-bucket permission right after deploy — by design
(`urb-agents#1802`), specifically so no second consumer can mint itself a new bucket with
it. Epinio therefore needs a genuinely new, dedicated key, imported (not generated by
Garage itself, so it can be managed the same way every other UIS secret is) and scoped to
its own bucket only.

## What was built

- **New secrets**: `EPINIO_GARAGE_ACCESS_KEY`/`EPINIO_GARAGE_SECRET_KEY` added to
  `00-master-secrets.yml.template` and `00-common-values.env.template`, following the
  exact convention `GARAGE_ACCESS_KEY`/`SECRET_KEY` already established — a separate pair,
  never reusing the bootstrap one.
- **`ansible/playbooks/625-setup-epinio.yml`** — new tasks (8c-8k) that, idempotently:
  read the dedicated key and Garage's connection details from `urbalurba-secrets`; find
  the Garage pod; `garage key import <access> <secret> -n epinio --yes` if that key
  doesn't already exist (exact flags confirmed against Garage's own CLI source,
  `src/garage/cli/structs.rs` `KeyImportOpt`, tag v2.3.0 — not guessed); `garage bucket
  create epinio` if the bucket doesn't exist; `garage bucket allow --key epinio --read
  --write epinio` (idempotent by nature, matches `047-setup-garage.yml`'s own
  `deny --create-bucket` task shape — always run, no existence check needed). The Helm
  values this playbook writes then set `seaweedfs.enabled: false` and a real `s3:` block
  pointed at Garage with that dedicated key.
- **New static test**, `test-epinio-garage-s3-backend.sh` — asserts the S3 credentials
  come from the dedicated fact (never the raw bootstrap secret), the key import is
  existence-guarded (idempotent), the bucket grant is scoped to one bucket, and the
  Helm-values task carries `no_log` (the rendered content now includes a real secret).
  Mutation-tested: pointed the credentials at the bootstrap key instead (confirmed the
  test catches it), removed the idempotency guard (confirmed the test catches that too),
  restored both.
- `website/docs/services/management/epinio.md` updated with a short Storage section.

## Bug found live, fixed in PR #644

The `epinio` namespace's own `urbalurba-secrets` block in
`00-master-secrets.yml.template` was still a stale, never-updated empty `stringData: {}`
placeholder — a leftover from before this plan existed, left unpopulated when this plan
added `625-setup-epinio.yml`'s own read of `GARAGE_HOST`/`GARAGE_PORT`/
`EPINIO_GARAGE_ACCESS_KEY`/`EPINIO_GARAGE_SECRET_KEY` from exactly this namespace's own
copy of the secret (a separate object from the "default" namespace's copy of the same
key names — confirmed by every other namespace block in that file carrying its own real
`stringData`). `uis deploy epinio` failed outright before ever reaching Garage. Found
live by imac, patched container-locally to continue testing, reported as a separate bug
rather than silently worked around; populated for real in PR #644.

## Validation

**Met, live, 2026-10-27 (`urb-agents#2044`)**, once the bug above was worked around:
`uis deploy epinio` ran the whole Garage sequence clean — imported Epinio's dedicated
key, created the `epinio` bucket, granted read+write, all idempotently (a full re-deploy
produced zero duplicate keys/buckets, confirmed directly via `garage key list`/`bucket
list`, not just the playbook's own "changed" count). Pushed a real app — its bucket
genuinely received real data (`garage bucket info epinio`: 0 B/0 objects before, 3.1
kB/1 object after). Decoded `epinio-s3-connection-details` directly: real endpoint, real
dedicated key, not the bootstrap one. This was run against imac's own container-local
patch for the bug above, not the code as it stood in the repo at the time; PR #644 makes
that same fix for real, so the shipped code now matches what was actually tested, but
has not been independently re-run against a live cluster since.
